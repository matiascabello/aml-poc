  Data model

  Alert — everything the LLM/analyst sees. No hint of the "right answer"
  anywhere in it.

  Alert
  ├─ alert_id            str   e.g. "ALERT-001"
  ├─ flagged_at           date  when the monitoring system raised it
  ├─ red_flag
  │   ├─ code             str   GAFI/FATF category, e.g. "STRUCTURING",
  "RAPID_MOVEMENT",
  │   │                         "HIGH_RISK_JURISDICTION", "PROFILE_MISMATCH",
  "UNUSUAL_FOR_PROFILE"
  │   └─ description       str   one-line plain description of why the rule
  fired
  ├─ customer   (KYC profile as declared/on file — not verified truth)
  │   ├─ customer_id       str
  │   ├─ full_name         str
  │   ├─ country            str   ISO2, e.g. "AR", "UY", "PY"
  │   ├─ customer_since     date
  │   ├─ declared_occupation        str
  │   ├─ declared_monthly_income_usd  number
  │   ├─ employer           str | null
  │   ├─ is_pep             bool   politically exposed person
  │   ├─ risk_rating        "low" | "medium" | "high"   (KYC rating assigned at
  onboarding)
  │   └─ account_type       str   e.g. "personal_checking", "business_checking"
  └─ transactions[]   (the ones that triggered/surround the alert)
      ├─ tx_id              str
      ├─ date                date
      ├─ type                "cash_deposit" | "cash_withdrawal" | "wire_in" |
  "wire_out" | "internal_transfer"
      ├─ amount_usd          number
      ├─ channel             "branch_cash" | "wire" | "online" | "atm"
      ├─ counterparty_name   str | null
      ├─ counterparty_country str | null
      └─ notes               str | null   (free text, e.g. memo line on a wire)

  GroundTruth — kept in a separate structure/file, keyed by alert_id. The
  analyzer never receives this; only the eval step reads it.

  GroundTruth
  ├─ alert_id                str    matches Alert.alert_id
  ├─ expected_recommendation "escalate" | "dismiss"
  ├─ difficulty              "clear_suspicious" | "clear_innocent" | "ambiguous"
  └─ rationale                str   what a good narrative should reference —
  used to grade the LLM's narrative quality in step 4, not just the label

  A few deliberate choices:
  - customer fields are all declared/on-file, not ground truth about the person
  — that mismatch between declared profile and actual transaction behavior is
  precisely what the LLM has to reason about.
  - red_flag tells the LLM which rule fired, but not whether it's a true or
  false positive — that's the recommendation it has to produce.
  - risk_rating and is_pep are onboarding-time KYC fields (real inputs an
  analyst would have), not spoilers.

⏺ Where the lock actually lives

  Trace the call path, in order:

  1. state_machine.py enforces legal workflow shape — ALLOWED_TRANSITIONS is a
  dict from each state to the set of states it may move to next
  (rejected/executed map to set(), i.e. terminal). Every mutation goes through
  _transition(), which checks that dict and raises InvalidTransitionError if the
  move isn't listed — this is what stops pending → executed, double-approve(),
  resurrecting a rejected alert, etc.
  2. gate.py::ensure_approved() is the actual lock: one function, one if,
  checking alert.state is not AlertState.APPROVED. It doesn't know about the UI,
  the analyst, or the LLM — it only reads the object's current state.
  3. execute.py::execute() calls ensure_approved(alert) as its first line,
  before touching anything else. That's the load-bearing line — everything below
  it (deciding file_ros vs close_alert, building the stub result, calling
  alert.mark_executed(...)) is unreachable unless that line passes.

  Why this holds even bypassing the UI: execute() is a plain function taking a
  TriageAlert object. There's no second code path, no service layer, no "trusted
  caller" flag — calling it directly from a test, a script, or a debugger hits
  the exact same ensure_approved() check a UI button would. That's proven by
  test_execute_on_non_approved_alert_raises_even_when_called_directly,
  parametrized over all four non-approved states (pending, analyzed, rejected,
  already_executed) — plus
  test_double_execute_is_refused_by_the_gate_not_just_the_state_machine, which
  shows the gate re-checks on every call, not just the first.

  One more thing worth noting: mark_executed() on TriageAlert is a state-machine
  primitive, not the lock itself — nothing stops something else from calling it
  directly and lying about having filed a ROS. The audit log would still show
  it happened, but the guarantee in CLAUDE.md is specifically about execute(),
  the function that performs the effectful action — and that one is airtight. If
  you want mark_executed() itself un-callable except from within execute(),
  that's a small follow-up (e.g. a private convention or moving the transition
  inline into execute()); I left it as a visible method for testability and
  audit-log clarity, but flag if you'd rather tighten it now before we move to

  ---
  1. Recommendation correctness

  Framing: positive class = escalate (the "alarm"). Two error types:

  - False Negative (FN) — ground truth escalate, model says dismiss. A truly
  suspicious alert gets silently closed. Nobody reviews it again. This is the
  dangerous direction.
  - False Positive (FP) — ground truth dismiss, model says escalate. Costs an
  analyst a few minutes to review and clear. Annoying, not dangerous — the human
  gate (already built in step 2) catches it before anything happens.

  That asymmetry is the whole point of your instruction, so it drives the
  thresholds directly rather than a blended accuracy number.

  Reporting shape: always the full per-alert table first —

  alert_id | difficulty | ground_truth | predicted | result (TP/FP/FN/TN)

  — then a breakdown by difficulty tier, never a single headline percentage.

  Thresholds, stated as gates rather than a percentage:

  1. Zero-FN gate (hard fail). Any escalate-labeled alert predicted dismiss —
  whether it's clear_suspicious or ambiguous — fails the eval run outright.
  Report exactly which alert_id(s). No partial credit, no averaging it away
  against correct calls elsewhere.
  2. Discrimination gate (hard fail). At least one of the two clear_innocent
  alerts must be correctly dismissed. This exists specifically to catch the
  degenerate "always escalate" policy — that policy trivially passes gate 1 with
  0 FN, so gate 1 alone is gameable. Zero correct dismissals = fail,
  independent of everything else.
  3. Soft target (not gating, just tracked). Both clear_innocent alerts
  dismissed (0 FP total). A single FP is logged as "analyst overhead," not a
  failure — but the point is regressions here still get seen, not silently
  absorbed into a passing aggregate.

  Why the difficulty breakdown matters here specifically: a FN gate is failing
  across all escalate-labeled alerts, but where it fails changes the read. A
  miss on clear_suspicious means the model is unreliable on the easy case —
  that's alarming. A miss on ambiguous means it under-called a genuinely hard
  judgment case — still a gate failure by this ground truth, but the fix is
  probably "look at the narrative it wrote and see if it engaged with the
  ambiguity at all," not "something is fundamentally broken." The report should
  make that distinction visible, not just say "1 FN."

  On percentages with N=6: I'd refuse to headline one. 6 examples means each
  alert is ~17 percentage points — "83% accuracy" and "one specific miss on
  ALERT-004" are the same fact, and the percentage actively hides which one it
  was. If a single number is wanted for a dashboard later, report it as k/6 
  exact match with the FN/FP breakdown mandatorily attached, never alone.

  ---
  2. Narrative quality

  CLAUDE.md's bar: cites the specific reason, breaks down evidence by
  amount/date/counterparty; bad = generic or "defensive."

  Design: two layers, only one of which runs in fake mode.

  Layer 1 — deterministic rubric (built and run now)

  Pure code, no LLM, checks the narrative text against facts pulled straight
  from the AlertData it's about:

  Check: Cites a specific amount
  Pass condition: At least one dollar figure from
  alert.transactions[*].amount_usd appears in the narrative
  ────────────────────────────────────────
  Check: Cites a specific date
  Pass condition: At least one date from alert.transactions[*].date (or
  flagged_at) appears
  ────────────────────────────────────────
  Check: References the customer's profile
  Pass condition: Occupation, declared income, or employer is named/quoted —
  this
  is the "cross-reference against the profile" requirement, not just
  evidence-dumping
  ────────────────────────────────────────
  Check: References counterparty/jurisdiction
  Pass condition: When the alert's transactions have a
  counterparty_name/counterparty_country, at least one is named. Skipped (N/A) 
  for alerts with no counterparty data, e.g. ALERT-001's cash deposits

  Score = fraction of applicable checks passed (3 or 4 checks depending on the
  alert). Threshold: 100% of applicable checks, every alert. These are low-bar,
  mechanical citations — anything short of full marks is a real defect per the
  regulator's own stated bar, not a nitpick.

  Report shape: per-alert row of ✓/✗ per check, not a blended score — so a
  failure reads as "ALERT-003 narrative never cites a specific date," not
  "narrative scored 3/4."

  Explicit limitation, stated up front: this rubric proves the narrative touches
  the right facts. It does not prove the reasoning connecting them is sound — a
  narrative could cite the right amount and date and counterparty and still
  draw the wrong conclusion, or list facts without actually arguing why they
  matter (the "defensive" failure mode CLAUDE.md warns about specifically
  resists a keyword check). That gap is real and Layer 2 exists to close it.

  Layer 2 — LLM-as-judge (designed, not built or run this step)

  Deliberately deferred — running a judge means a real model call, which
  contradicts "before any real LLM is involved." Design now so it's a drop-in
  later, same pattern as LLM_MODE:

  - A JudgeClient interface mirroring LLMClient, with its own
  JUDGE_MODE=fake|real — a FakeJudgeClient can return canned scores now if we
  want to exercise the plumbing, RealJudgeClient comes later.
  - Judge prompt scores narrative coherence/adequacy 1–5 against the CLAUDE.md
  rubric text directly (specific reasoning vs. generic/defensive), not just fact
  presence.
  - Determinism tradeoff, and how I'd handle it:
    - Temperature=0 at the API level, but that alone doesn't guarantee
  bit-identical output across calls or model versions — pin and log the exact
  judge model version in the eval report.
    - Run the judge k=3 times per narrative, report the median score and the
  spread. Disagreement across the 3 runs is itself a signal (a narrative the
  judge scores 2/4/5 is ambiguous to grade, not just ambiguous to write) — log
  it, don't average it away silently.
    - Advisory only — never gates pass/fail. The deterministic rubric (Layer 1)
  is what decides pass/fail for the eval suite, because gating on a
  nondeterministic score would undermine the exact thing you asked for this
  step: an eval trusted deterministically. The judge score sits alongside as a
  secondary quality signal for a human to read.
    - Self-grading bias: once RealLLMClient exists, the judge should ideally be
  a different model/provider than the analyzer, or at minimum this is logged as
  a known limitation if cost forces the same family.

  ---
  3. Eval machinery trustworthiness (before pointing it at the 6 alerts)

  Same principle as step 2's harness: the scoring logic itself gets unit tests
  on synthetic fixtures, independent of the real alert set — e.g., feed the
  rubric checker a narrative that's missing every dollar figure and assert it
  fails check 1; feed the confusion-matrix logic a forced mismatch and assert
  it's classified as FN not FP; assert the zero-FN gate actually fails the run
  when a canned prediction is wrong. That's what "trusted deterministically"
  means concretely: the grader is proven correct on cases where we already know
  the right answer, before it's trusted on the 6 example alerts.

  ---
  4. Output shape (for approval, not built yet)

  A single eval report with, in this order:
  1. Per-alert recommendation table (ground truth / predicted / TP·FP·FN·TN)
  2. Gate results: zero-FN gate (PASS/FAIL + offending IDs), discrimination gate
  (PASS/FAIL)
  3. Per-alert narrative rubric table (✓/✗ per applicable check)
  4. A "known limitations" footer, always printed, not just in docs: N=6 is not
  a statistical sample; the rubric is a fact-presence proxy, not a correctness
  proof; LLM-judge layer is designed but not active.
